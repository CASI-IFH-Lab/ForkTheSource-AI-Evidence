## What this changes

Adds the running skeleton: a Streamlit app that accepts a dropped PDF and renders the raw
text pdfplumber reads out of it, plus a `src/pipeline/` package with one module per stage
so the seven-stage pipeline has an obvious home. Also lands the config layer (B2): a
`config.yaml` holding every model name and temperature, and a loader that is the only
code in the repo permitted to read it.

No model is called anywhere in this branch. Five of the seven stages are docstrings and a
`raise`.

I got approval on:

**Say the word and I'll drop these.** Neither is load-bearing for anything else, both

## Reviewer's guide

**Arsha — read these three files and nothing else.** The diff is 709 lines across 20
files, but 462 of those are tests, a generated PDF fixture and docs. Three files carry
every decision worth arguing about, and they total 143 lines:

1. **`src/config.py` (79 lines)** — the B2 loader, and the file you will import from most.
   Check the **no-defaults rule**: there is no `.get(key, fallback)` anywhere, so a
   missing key raises instead of silently substituting a value. Then check
   `temperature_for()`, which reads a *different key* (`critic_temperature`) when the
   stage is `critic` — that is the one piece of non-obvious behaviour in the file, and if
   you disagree with hiding it behind the stage name, now is the moment.
2. **`src/llm.py` (32 lines)** — the gateway client. Check that the base URL has **no
   default in code** (it comes only from `AIR_BASE_URL`; a default here would put the
   gateway hostname in `src/` and fail the ground-rule grep), and that both missing-env
   errors name the variable and point at `.env.example`.
3. **`src/pipeline/__init__.py` (32 lines)** — the package docstring, which is the flow
   diagram and the `run(payload, config)` contract, plus the `STAGES` tuple. This is the
   shape B1 has to interoperate with. If the stage boundaries are wrong, this is the file
   that says so.

**Skim or skip:** `app.py` (Streamlit glue, ~70 lines, no logic), the five stub stages
(docstring + `raise`, ~14 lines each), all four test files, `tests/data/sample.pdf` and
its generator, and `docs/` (written for the team, not for review).

## Anything I was unsure about

- **The `judge.run` signature is missing the plan's `fallback_fn` seam**, and there is no
  orchestrator module for the `judge_fn` seam to live on. Both were left alone
  deliberately — changing a stage signature is P-lane feature work, not B0 — and both are
  recorded in
  [`docs/pipeline_stages.md`](../pipeline_stages.md#dependency-injection-seams) and in
  the deviations list in `docs/module_status.md`. **Flagging in case you would rather the
  seams land with B0** so nobody merges a judge without them.
- **`intake.run(pdf, config=None)`** takes `config` as optional and ignores it, where the
  other six take it as required-positional. Harmless today, but the orchestrator will
  want all seven callable identically.
- **The Module Implementation Plan is not in the repo**, so the module-ID mapping in the
  docs (which of P1-P6 fills which stage, and who owns A2/A3/R1/R3/B3) is inferred from
  the task brief and marked `inferred` or `confirm` wherever it is not verified against
  the tree. Worth one pass before the team reads those docs as authoritative.
