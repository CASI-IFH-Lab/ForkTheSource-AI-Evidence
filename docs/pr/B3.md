## How I tested

There is no code to test, so verification was: does `EXAMPLE.json` actually satisfy the
spec I wrote? I walked it through FORMAT.md's 9-point checklist mechanically rather than by
eye, and **it failed on the first item**, which is why the spec now has an exemption
section:

```
  1. PASS  exempt from the stem==document rule (documented specimen)
  2. PASS  6 labels for a 6-reference paper, one each
  3. PASS  ref_ids consecutive from R01, no gaps or duplicates: R01 R02 R03 R04 R05 R06
  4. PASS  every expected_status is one of the four, exact lower case
  5. PASS  every indicator is one of the six, exact lower case, no duplicates in an array
  6. PASS  defect present iff injected is true; no unrecognised keys anywhere
  7. PASS  N/A - specimen, not part of the 21-defect count
  8. PASS  N/A - specimen, not the clean control
  9. PASS  injected:false + unresolvable present at ['R06'] - the documented exception

  four statuses      : ['conflict', 'needs_check', 'unresolvable', 'verified']
  indicators (4 >= 3): ['doi_mismatch', 'malformed', 'orphan', 'version_mismatch']
```

Two things that check found, both now fixed in the spec:

1. **`EXAMPLE.json`'s stem does not match its `document` field**, and R1's card has R2
   globbing `eval/golden/*.json` — so the harness would pick up the specimen, look for a
   ledger for a paper that will never exist, and fail on a file meant only for humans.
   FORMAT.md now names the exemption and tells R2 to skip the file, with the alternative
   of relocating it.
2. **21 injections but 23 labelled rows.** Each duplicate-entry defect is one injection
   producing two labelled entries. A validation step that checks the `injected: true`
   count against 21 will report two missing labels forever. Recorded in both files.

## Statuses and indicators touched

All four statuses and all six indicators appear, as **specification text and expected
values only**. No code classifies anything here. The vocabulary is treated as closed and
frozen: `verified`, `needs_check`, `conflict`, `unresolvable`; `retracted`,
`version_mismatch`, `doi_mismatch`, `duplicate_entry`, `orphan`, `malformed`.

The exact strings matter because R2 compares them to contract enum values by string
equality, so FORMAT.md also specifies that `ref_id` is compared as an **opaque string** —
`"R03"` and `"R3"` are different ids — and that indicator arrays are compared as **sets**.

## Ambiguities — the part I most need reviewed

Nine places where a defect type does not map cleanly onto one status and one indicator
set. Each is a decision R2's harness will otherwise make silently, and a silent decision in
ground truth is how a metrics slide becomes wrong without anyone noticing. I picked a
default for every one and documented it; four need Roy's confirmation.

1. **Wrong-year and version-pair both produce `version_mismatch`** with different expected
   statuses. There is no `year_mismatch` in the closed vocabulary, and `version_mismatch`
   is defined as "title+authors strong but venue/year differ", which a wrong-year defect
   satisfies literally. The pipeline has no signal that separates them. **Needs a decision.**
2. **Hallucinated references are indistinguishable from legitimate unresolvable ones** —
   both are `unresolvable` + `[]`. Recall on this type is only meaningful because we know
   which `ref_id`s we fabricated.
3. **Mangled author lists have no indicator.** Nothing in the six covers author divergence,
   so the status is the only signal. Also masked entirely by a matching DOI, hence the
   instruction to inject only on DOI-less references.
4. **A duplicate-entry defect produces two labelled entries from one injection.** Hence 21
   vs 23. Also unsettled: `needs_check` + `[duplicate_entry]` on both, or `verified` +
   `[duplicate_entry]` on the grounds that both copies resolve fine?
5. **Malformed entries: `unresolvable` or `needs_check`?** P5's mapping says "no resolved →
   unresolvable"; A1's prompt rules say parse noise moves confidence toward `needs_check`.
   Both are in the plan and they disagree. I chose `unresolvable`. **Needs a decision.**
6. **Orphan has no defined status.** P5's status mapping does not mention it. I chose
   `verified` + `[orphan]` — the work exists, being uncited is hygiene, not doubt.
7. **The version pair has two permitted statuses in the plan itself**
   ("verified-with-indicator or needs_check") and the one-defect-one-status rule forces a
   choice. I chose `verified` + `[version_mismatch]`. **Needs a decision.**
8. **Are the two version-pair traps part of the 21?** Their correct outcome is `verified`,
   which is not a detection, so a recall denominator containing them mixes two
   measurements. **Needs a decision.**
9. **What counts as a false accusation for the release-blocking check?** I assumed
   `conflict` on an `injected: false` reference and nothing else — `needs_check` on a clean
   reference is a false *alarm* worth a separate non-blocking metric, but conflating them
   makes the gate fire on the tool being appropriately cautious.

Two more open questions in FORMAT.md are R2's to answer, not R1's: what `document` matches
against (`Ledger.document_name` or the PDF filename), and exact-set versus subset indicator
matching.

## Anything I was unsure about

- **I am not the right author for this module.** The injection methods are written as
  instructions to someone else, but they have never been executed, and some will turn out
  to be awkward on real PDFs — particularly editing reference sections in a way that
  survives pdfplumber extraction. Expect the catalog to need edits during R1, and treat
  that as normal rather than as this PR being wrong.
- **The distribution of 7-7-7 across three papers is my choice, not the plan's.** The plan
  says "~21 across three papers" and nothing more. Even spreading exercises most of the
  vocabulary per paper without making any single paper implausibly broken, but a different
  split may suit the papers Roy picks.
- **No paper titles, fields, or citation styles are assumed anywhere** — deliberately. The
  one place it matters is the orphan diagnostic in section 6, which depends on knowing
  whether the corpus uses numeric or author-year citations.
- **The plan PDF is not on `main` yet.** It lands with B0 (queue #1), so the references to
  `docs/module_implementation_plan.pdf` in both files are dangling until then. Noted inline
  in both rather than left as broken links.
