## 🔴 The one open item, and it constrains unwritten code

**`version_mismatch` fires when exactly ONE of the two records is a preprint** — a
preprint-server venue name (arXiv, bioRxiv, medRxiv, SSRN, or similar) or the presence of an
arXiv ID. It does **not** fire on venue string divergence, and it does **not** fire on year
divergence.

**This constrains P5 step 2, which is unwritten, and it is on the Sync 1 agenda.** Ruled as
**D-020** in `docs/decisions.md`. It is the only place in this PR where the corpus imposes a
requirement on the pipeline rather than merely describing it.

**D-020 is a reversal.** An earlier ruling in this branch required *venue divergence*; that
was wrong for two reasons. Venue strings are the least normalised field in any bibliography
— `Journal of Machine Learning Research` and `J. Mach. Learn. Res.` are the same venue and
differ on every character comparison — so implemented as string inequality the indicator
would fire on **correctly-cited references throughout the corpus, including the clean
control**, the one paper whose false-accusation count has to be zero. And implemented as
venue *similarity* it needs a threshold that does not exist: `config.yaml`'s four matching
keys are `title_strong`, `title_weak`, `author_strong` and `year_tolerance`, so a similarity
test means either a fifth config key or a hardcoded comparison. The categorical test is a
boolean, needs neither, is immune to abbreviation noise, and encodes the plan's own words
("preprint vs journal") rather than a proxy for them.

**Every label in this PR is identical under either formulation.** Only the code that has to
satisfy them changes — which is why this is safe to merge now and settle at Sync 1.

What breaks if P5 sets the indicator on year divergence instead: `D07`-`D09` come back as
`needs_check` + `[version_mismatch]` against a label of `needs_check` + `[]`, and because
indicator matching is exact-set, **all three score as misses on a correct classification**.
Recall drops to 18/21 and fails the plan's ≥ 19/21 target while the pipeline is behaving
properly.

## The 21-vs-23 distinction, and how `defect_id` resolves it

These are two different numbers and conflating them silently corrupts recall:

- **21 injections.** This is the recall denominator, and it is the plan's "~21 across three
  papers".
- **23 label rows** with `injected: true`. Two defects occupy two rows each — a duplicate
  entry is by definition two bibliography rows — so rows exceed injections by two.

**Recall is measured over `defect_id`s, not over rows.** Each injection gets one
`defect_id`, assigned in the catalog now and globally unique across the corpus. The rows of
a multi-row defect share its id.

**A `defect_id` counts as matched only when ALL of its rows match** — both status and
indicator set, on every row. Half-detecting a duplicate pair is not half a detection; it is
a miss. Catching one row of `D06` and missing the other means the pipeline did not
understand that the two rows are the same defect, which is exactly the failure the label is
there to catch. Scoring it as 0.5 would report partial credit for a wrong answer.

This is why the resolution is a field and not a string-matching convention: R2 groups rows
by `defect_id` and requires unanimity within the group. Nothing has to parse the `defect`
free text, which FORMAT.md is explicit is never scored.

## `eval/corpus/originals/` stays TRACKED — corrected in this branch

The originals are **committed**, not gitignored. `.gitignore` excludes `eval/outputs/` only,
and nothing under `eval/corpus/` is ignored. Two reasons, both now written into the catalog:

- **R1 step 3 diffs each spiked PDF against its original**, so the original must be in the
  tree for anyone but the injector to reproduce the diff.
- **R2 may check that `source.origin_file` exists.** Gitignoring the originals makes that
  check pass on the machine that wrote the labels and fail on every clone — the worst kind
  of green.

**Escape hatch, also now in the catalog:** if any original exceeds **~10 MB**, store the
**arXiv ID (or DOI) plus a fetch script** under `eval/corpus/originals/` instead of the PDF,
and point `source.origin_file` at the stub. A large binary in git history is permanent, and
three people clone this repo.

## Schema extension — four fields beyond the plan's example

The plan's example is a minimum shape and specifying this format *is* B3's job. Each field
exists to stop R2 inferring something from the `defect` free text.

| Field | Where | Required | Why it exists |
|-------|-------|----------|---------------|
| `defect_id` | per label | when `injected: true` | Resolves 21 vs 23 without string matching. See the section above. |
| `control` | top level | yes | R2's release-blocking check must **read** which file is the control, never infer it from "every label is `injected: false`" — that inference breaks the moment a spiked paper is committed before its labels are written. |
| `source` | top level | yes | `{license, origin_url, origin_file}`. Makes R1's *"no copyright-restricted or student material"* DoD box **verifiable from the tree** rather than asserted in a PR. `license` is one of five allowed strings; a value outside the set is a hard error. |
| `verified_by` / `verified_on` | per label | no | The audit trail for R1's *"a teammate spot-verifies 5 random labels"* test plan. Optional because most labels will never be spot-checked; present so the ones that were are recoverable months later. |

## Two gaps accepted as gaps

Both were considered; neither is being fixed. Recorded in FORMAT.md so nobody shoehorns them
in later.

1. **Document-level defects stay out.** P1's no-heading fallback has no `ref_id` to attach
   to, and injecting it would re-index every other label in the file. It belongs in a
   separate fixture PDF under `tests/`, **owned by P1**.
2. **`confidence`, `priority` and `checks[]` stay unlabelled** — labelling a confidence
   number would pin ground truth to an uncalibrated scale. But the **worklist is assertable
   from the labels that already exist**, with no new field: every reference in the top-3
   worklist must have `injected: true`, and no version-pair trap may appear in it (it is
   `verified`, severity `0.0`, so it belongs at the bottom). That catches the failure where
   per-status precision and recall both pass while the ordering a reviewer actually looks at
   is wrong — and the top-3 worklist is a demo beat.
